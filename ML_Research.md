# ML Research — Система рекомендации подарков

Документ описывает полный путь от сырых данных до работающей ML-модели в production:
откуда взялись данные, как они обработаны, на каком алгоритме и почему именно на нём
работает ранжировщик, и какие технологии выбраны для каждого слоя.

---

## 1. Постановка задачи

### 1.1. Что мы решаем

Задача — **персонализированный подбор подарков**. Пользователь заполняет анкету:
повод (день рождения, Новый год, …), отношения с получателем (друг, коллега, родитель),
возраст, пол, интересы и бюджет. Сервис должен вернуть топ-N подарков, максимально
соответствующих этим критериям.

С точки зрения ML это классическая задача **ранжирования** (Learning-to-Rank, LTR):
для каждого запроса есть множество кандидатов (товары из каталога), и надо упорядочить
их по убыванию релевантности.

### 1.2. Почему не рекомендательная фильтрация (Collaborative Filtering)

Collaborative Filtering (CF) требует матрицу пользователь × товар с историей взаимодействий.
На старте сервиса:
- история пустая (холодный старт для товаров **и** пользователей)
- каталог обновляется регулярно (новые позиции не имеют истории)
- анонимные пользователи не дают сигнала для CF

LTR с контентными признаками работает с нуля и естественно учитывает явные критерии
анкеты (бюджет, возраст, интересы), что критично для UX — пользователь задал бюджет
500 ₽, и товар за 50 000 ₽ не должен попасть в топ.

### 1.3. Метрика качества — NDCG

Normalized Discounted Cumulative Gain (NDCG) используется потому, что:
- позиция имеет значение: первый подарок в списке увидит почти каждый, пятый — треть
- релевантность порядковая, не бинарная (товар может подходить «очень хорошо», «хорошо»
  или «слабо»), что DCG отражает через экспоненциальный вес `2^rel - 1`
- NDCG нормирует по идеальному ранжированию, позволяя сравнивать запросы разной длины

Целевые значения: **NDCG@5 ≥ 0.70** на синтетике, **≥ 0.75** после накопления трекинга.

## 2. Источники данных

### 2.1. Текущий датасет — синтетика

Файл `services/ml/dataset/dataset_example.csv` (10 000 строк) содержит
**синтетически сгенерированные** записи:

| Параметр | Значение |
|---|---|
| Записей | 10 000 |
| RU записи (RUB) | 5 000, id начинаются с `RU1` |
| CN записи (CNY) | 5 000, id начинаются с `CN5001` |
| Диапазон цен | 100–5998 в нац. валюте |
| Средняя цена | ~2 150 |
| Категорий | 10 |

**Почему синтетика на старте.** Реальные данные из Wildberries и AliExpress требуют
либо авторизации (Seller API), либо нестабильного парсинга публичных эндпоинтов.
Синтетика позволила сразу написать и протестировать весь pipeline — от feature engineering
до gRPC inference — не ожидая появления реальных данных.

**Важное ограничение.** Синтетические описания типа «Декоративный свеча 4998. Отличный
вариант подарка для разных случаев.» не несут семантической нагрузки. TF-IDF overlap
между интересами пользователя и текстом товара будет крайне низким, что снизит влияние
фичи `tfidf_score`. На реальных данных этот сигнал будет значительно богаче.

### 2.2. Планируемые источники реальных данных

**Wildberries** (`scripts/data/fetch_wb.py`):
- Использует публичный поисковый эндпоинт `https://search.wb.ru/exactmatch/ru/common/v4/search`
- Не требует авторизации, работает без API-ключей
- Возвращает: `name`, `priceU` (цена в копейках × 100), `subjectName` (категория), id товара
- Из id строится ссылка (`wildberries.ru/catalog/{id}/detail.aspx`) и URL изображения
  по шаблону с бакетированием (`id // 100000`)
- Ограничение: не официальный API; структура ответа может измениться

**AliExpress Affiliate API** (`scripts/data/fetch_aliexpress.py`):
- Официальный API (`aliexpress.affiliate.product.query`) через Aliexpress Open Platform
- Требует регистрации: `ALIEXPRESS_APP_KEY` + `ALIEXPRESS_APP_SECRET`
- Возвращает: `product_title`, `target_sale_price` в CNY, `first_level_category_name`,
  `promotion_link` (аффилиатная ссылка с трекингом), `product_main_image_url`
- Преимущество перед парсингом: стабильный контракт, официальная поддержка

**Почему именно WB и AliExpress, а не другие.** Это два крупнейших маркетплейса для
российского пользователя в 2025–2026 году, покрывающих RU и CN сегменты. Ozon закрыл
публичный API для внешних разработчиков, Яндекс.Маркет требует партнёрского статуса.
WB и AliExpress вместе дают достаточное разнообразие категорий и ценовых диапазонов
для MVP.

### 2.3. Нормализация — `normalize_to_catalog.py`

Скрипт приводит данные любого источника к единой схеме:

```
gift_id, title, description, category, price, currency, store_url, image_url, age_min, age_max
```

Ключевые операции:
1. **Маппинг категорий** (`category_mapping.yaml`) — WB и AliExpress используют
   собственные деревья категорий. Маппинг через keyword-matching приводит их к 10
   внутренним: `Электроника`, `Книги`, `Настольные игры`, `Косметика`, `Аксессуары`,
   `Одежда`, `Хобби`, `Украшения для дома`, `Еда и напитки`, `Детские товары`.
2. **Дедупликация по `store_url`** — один товар из двух источников не дублируется.
3. **Валидация** — строки с пустым `title`, нулевой ценой или невалидным URL отбрасываются.
4. **Нормализация цены** — всегда формат `NNNN.00` (две десятичных цифры), что совместимо
   с внутренним типом `Price` backend (хранит центы как `int64`).

### 2.4. Загрузка в каталог

Нормализованный CSV импортируется через существующий backend-эндпоинт
`POST /api/v1/admin/import-jobs`. Парсер (`catalogimport`) при этом:
- Создаёт запись в таблице `gifts` (канонические данные)
- Автоматически создаёт запись в `gift_offers` (задача #3) — связку «товар → магазин»,
  сохраняя оригинальный `store_url`, цену и валюту источника
- Определяет название магазина по URL: `wildberries.ru` → `Wildberries`,
  `aliexpress.com` → `AliExpress` и т.д.

## 3. Feature Engineering

Файл: `services/ml/ml_service/feature_builder.py`

### 3.1. Почему именно эти признаки

LTR модели обучаются на признаках, которые описывают **совместимость** (query, document).
Для нашей задачи «документ» — это товар, «запрос» — анкета пользователя.

Признаки можно разделить на три группы:

**Ценовые признаки** — самый сильный сигнал. Пользователь, задавший бюджет 1 000 ₽, никогда
не купит товар за 30 000 ₽, какими бы хорошими ни были остальные признаки.

| Признак | Как считается | Зачем |
|---|---|---|
| `price_within_budget` | `int(price ≤ budget)` | Жёсткое ограничение в виде признака |
| `budget_gap` | `max(0, budget − price)` | Больший зазор → товар «доступнее» |
| `budget_ratio` | `price / budget`, клип до 5.0 | Относительная дороговизна |
| `price_bucket` | Дискретный бакет [0..7] | Позволяет модели иметь нелинейный отклик на цену |
| `budget_bucket` | Дискретный бакет бюджета | Взаимодействие с `price_bucket` |

Клип `budget_ratio` до 5.0 предотвращает экстремальные значения, которые могут
дестабилизировать LambdaRank при масштабировании.

**Признаки соответствия профилю получателя:**

| Признак | Как считается | Зачем |
|---|---|---|
| `age_fits` | `int(age_min ≤ recipient_age ≤ age_max)` | Возрастное ограничение |
| `interest_overlap` | Кол-во совпадений токенов интересов с текстом товара | Грубая семантика |
| `tfidf_score` | Косинус между TF-IDF векторами интересов+повода и текста товара | Более точное семантическое соответствие |

**Признаки категории:**

| Признак | Как считается | Зачем |
|---|---|---|
| `category_match` | `int(category == preferred_category)` | Прямое совпадение |
| `category_index` | Числовой индекс категории [0..9] | Позволяет модели учить per-category биас |
| `already_in_wishlist` | `int(gift_id ∈ wishlist)` | Штраф за уже сохранённые товары |

### 3.2. TF-IDF для текстового соответствия

Использован упрощённый TF-IDF — через **косинус пересечения токенов** (Jaccard-like):

```
sim(A, B) = |A ∩ B| / sqrt(|A| × |B|)
```

где `A` = токены интересов + повода, `B` = токены `title + description + category_name`.

**Почему не BERT/эмбеддинги?** На этапе MVP и при inference за ≤ 6 секунд для 200
кандидатов нагрузка на модель уже включает сам LightGBM predict. BERT-инференс на CPU
для каждой пары (запрос, кандидат) добавит 5–15 секунд. TF-IDF косинус вычисляется
за микросекунды на чистом Python.

При наличии GPU или выделенного embedding-сервиса (например, `sentence-transformers`
с кэшированием эмбеддингов товаров) — переход на семантические эмбеддинги увеличит
`tfidf_score` → `semantic_score` без изменения архитектуры pipeline.

### 3.3. Что НЕ включили и почему

- **Popularity** (`tracking_events` — клики, просмотры): на старте таблица пустая.
  После накопления 10k+ событий `popularity_score` добавляется в `FEATURE_COLS`.
- **Рейтинг и отзывы**: у нас нет отзывов из маркетплейсов — WB не отдаёт рейтинг
  в публичном поиске, AliExpress — только через платный API.
- **Сезонность**: признак "текущий месяц близок к поводу" — полезен, но требует
  маппинга повода на временной диапазон.

## 4. Синтез меток релевантности

Файл: `services/ml/training/synth_labels.py`

### 4.1. Проблема отсутствия размеченных данных

LTR требует разметку: для каждой пары (запрос, товар) нужна оценка релевантности.
В production эта разметка получается из **неявной обратной связи** (клики, добавления
в wishlist, переходы по ссылке). На старте это всё нулевое.

Решение — синтетический оракул: правила, которые симулируют «идеального» пользователя.

### 4.2. Шкала оценок [0..3]

Используется **порядковая шкала**, а не бинарная (0/1). Это важно: LambdaRank извлекает
сигнал из разницы позиций, и три уровня «хорошести» дают ему больше градиентов для
обучения, чем два.

| Метка | Условие | Смысл |
|---|---|---|
| 0 | `price > budget` | Нерелевантен полностью |
| 1 | В бюджете | Слабое соответствие |
| 2 | В бюджете + (категория ИЛИ возраст) | Хорошее соответствие |
| 3 | В бюджете + категория + возраст | Отличное соответствие |

**Ключевое правило**: `price > budget` сразу даёт метку 0, ничто другое не компенсирует.
Это соответствует реальному поведению — пользователь не купит товар дороже бюджета.

### 4.3. Генерация синтетических запросов

```
n_queries запросов × ~50 кандидатов = ~50n_queries строк
```

Каждый запрос случайно выбирает:
- Повод из 6 вариантов (день рождения, Новый год, 8 Марта, …)
- Отношения из 5 (друг, коллега, родитель, …)
- Возрастную группу: [0–12], [13–17], [18–30], [31–50], [51–99]
- Бюджет: 1 000, 2 000, 3 000, 5 000, 10 000, 15 000, 20 000 ₽
- Интересы: 2 слова из словаря для категории

Словарь `INTEREST_MAP` привязывает категории к ключевым словам:
```python
"Электроника": ["гаджет", "смартфон", "наушники", "ноутбук", "электроника"]
"Книги":       ["книга", "литература", "чтение", "роман", "учеба"]
...
```

Для каждого запроса из каталога случайно сэмплируется 50 товаров. Это имитирует
этап **candidate generation** — в реальной системе backend делает `SELECT ... LIMIT 400`
с жёсткими фильтрами, затем ML видит 200 лучших кандидатов.

### 4.4. Распределение меток (на 1 000 запросов × 50 кандидатов)

```
{2: 10376, 1: 8899, 0: 5306, 3: 419}
```

Метка 3 редкая (~1.7%) — это нормально для LTR: "идеально подходящих" товаров мало.
Дисбаланс классов не критичен для LambdaRank, т.к. она оптимизирует попарные отношения,
а не распределение классов.

## 5. Подготовка датасета

Файл: `services/ml/training/prepare_dataset.py`

### 5.1. Добавление признаков к сырым меткам

`synth_labels.py` создаёт сырой датасет (query, gift, label). `prepare_dataset.py`
дополняет его всеми признаками из `feature_builder.py`, применяя те же функции,
что используются при inference, — это **ключевой принцип**: train/serve consistency.

### 5.2. Разбивка train/validation

```python
# Разбивка по query_id, НЕ по строкам
query_ids = df["query_id"].unique()
np.random.shuffle(query_ids)
train_qids = query_ids[:85%]
val_qids   = query_ids[15%:]
```

**Почему по query_id, а не по строкам?** Если разбить по строкам, то строки одного
запроса попадут и в train, и в val. Модель «увидит» во время обучения частичный паттерн
запроса, а на валидации оценит его же — это data leakage. Разбивка по `query_id`
гарантирует, что validation содержит только **новые** запросы.

## 6. Модель: LightGBM LambdaMART

Файл: `services/ml/training/train_lightgbm.py`

### 6.1. Почему LTR, а не классификация/регрессия

Классификация на 4 класса обучалась бы предсказывать метку каждого товара независимо —
но нам нужен **порядок** внутри запроса, а не абсолютные оценки. Регрессия ближе,
но тоже оптимизирует MSE на отдельных примерах, игнорируя попарные отношения.

LTR напрямую оптимизирует ранговые метрики через попарные или листовые функции потерь.

### 6.2. Почему LightGBM, а не XGBoost или CatBoost

Рассматривалось три варианта:

| Библиотека | Сильные стороны | Почему не выбрали / выбрали |
|---|---|---|
| **XGBoost** | Проверен годами, хорошая документация | Медленнее LightGBM на больших данных, нет встроенного LambdaRank в новых версиях |
| **CatBoost** | Хорошо с категориальными фичами, YetiRank | Тяжелее (~150 MB), медленнее inference для нашего объёма |
| **LightGBM** | Быстрый train и inference, листовой рост дерева (leaf-wise), встроенный LambdaRank | **Выбран** |

LightGBM:
- **Leaf-wise growth** (в отличие от depth-wise в XGBoost): глубже разбивает листы с наибольшим приростом, что даёт более точные деревья при том же числе листьев
- **Histogram-based splitting**: квантизует признаки в корзины перед построением — скорость тренировки на порядок выше при сравнимом качестве
- `lightgbm` весит ~20 MB и имеет inference < 5ms для 200 кандидатов на CPU, что укладывается в SLA ≤ 6 секунд

### 6.3. LambdaMART — функция потерь

`objective = "lambdarank"` в LightGBM реализует **LambdaMART** — алгоритм,
который комбинирует:
- **LambdaRank**: попарные градиенты, взвешенные изменением NDCG при перестановке пары
- **MART** (Multiple Additive Regression Trees): GBDT-фреймворк, где каждое новое дерево
  аппроксимирует псевдо-градиенты из LambdaRank

**Ключевое свойство LambdaMART**: градиент для пары (i, j) масштабируется на
`|ΔNDCG|` — изменение NDCG при обмене местами i и j. Это означает, что модель больше
наказывается за перестановку в верхней части списка, чем в нижней. Именно так и должно
быть: переставить позиции 1 и 2 важнее, чем 8 и 9.

### 6.4. Гиперпараметры

```python
params = {
    "objective":      "lambdarank",
    "metric":         "ndcg",
    "ndcg_eval_at":   [5, 10],
    "learning_rate":  0.05,
    "num_leaves":     31,
    "min_data_in_leaf": 5,
    "seed":           42,
}
num_boost_round = 200
early_stopping  = 20
```

**`learning_rate = 0.05`** — консервативный шаг. Более высокий (0.1+) ускоряет
сходимость, но склонен к переобучению на синтетике с малым числом уникальных паттернов.

**`num_leaves = 31`** — дефолтное значение LightGBM, соответствует глубине ~5. Для 9
признаков этого достаточно: больше листьев дало бы переобучение.

**`min_data_in_leaf = 5`** — защита от переобучения на редких паттернах.

**`early_stopping = 20`** — если NDCG@5 на валидации не улучшается 20 раундов,
обучение останавливается. Это позволяет `num_boost_round = 200` служить верхней границей,
а не фиксированным числом итераций.

**`seed = 42`** — фиксированный сид для воспроизводимости (используется в numpy,
LightGBM и разбивке данных).

### 6.5. Оценка качества — NDCG

```python
def ndcg_at_k(labels, k):
    dcg  = Σ (2^rel_i - 1) / log2(i + 2)   # по первым k позициям
    idcg = DCG идеального порядка
    return dcg / idcg
```

На синтетическом датасете (1 000 запросов) ожидаемые значения:
- **NDCG@5 ≥ 0.72–0.80**: синтетические метки детерминированы правилами, которые
  напрямую отражены в признаках — `price_within_budget`, `category_match`, `age_fits`.
  Модель по сути выучивает эти правила обратно.
- **NDCG@10 ≥ 0.70–0.78**: чуть ниже, т.к. позиции 6–10 важны меньше и градиент
  LambdaMART там слабее.

## 7. Inference pipeline

Файл: `services/ml/ml_service/grpc_server.py`

### 7.1. Путь запроса

```
Backend (Go)
  └─ POST /api/v1/recommendations (анкета пользователя)
       └─ recommendation/usecase: отбирает ≤200 кандидатов из БД
            └─ gRPC RankRequest → ML service (порт 50051)
                 └─ feature_builder.build_features(request)  → list[dict]
                 └─ Ranker.predict(features)                 → list[float]
                 └─ сортировка по убыванию score
                 └─ top_n, alternatives (TF-IDF cosine)
                 └─ explainer.explain(candidate, query, features)
            └─ RankResponse → backend
       └─ сохраняет результат в БД
  └─ JSON response пользователю
```

### 7.2. Feature builder при inference

При inference `feature_builder.build_features(request: RankRequest)` принимает
protobuf-сообщение и возвращает `list[dict]` — один словарь на кандидата.
Ключи словаря строго совпадают с `FEATURE_COLS` в training-скрипте.

**Критично**: `FEATURE_COLS` определён **в двух местах** — в `feature_builder.py`
(inference) и `train_lightgbm.py` (training). При добавлении нового признака нужно
менять оба файла одновременно.

### 7.3. Альтернативы через TF-IDF cosine

Для каждого товара из топ-N вычисляются «альтернативы» — похожие товары, не вошедшие
в топ. Сходство меряется косинусом между множествами токенов:

```python
sim(a, b) = |tokens(a) ∩ tokens(b)| / sqrt(|tokens(a)| × |tokens(b)|)
```

где `tokens(x)` = все слова из `title + description + category_name` товара x.

Берутся 2 наиболее похожих кандидата, не занятых в топ-N. Это дёшево (O(m) по числу
кандидатов) и не требует отдельной матрицы эмбеддингов.

### 7.4. Объяснения рекомендаций

`explainer.py` генерирует текстовые объяснения на основе признаков:

| Условие | Объяснение |
|---|---|
| `price_within_budget` | «Подходит по бюджету.» |
| `interest_overlap > 0` | «Соотносится с интересами.» |
| `tfidf_score > 0.1` | «Релевантен запросу.» |
| `age_fits` и задан возраст | «Учитывает возраст получателя.» |
| `category_match` | «Совпадает с категорией.» |

Это **не SHAP** (SHapley Additive exPlanations) — SHAP даёт точный вклад каждого
признака в предсказание, но требует отдельного прохода через все деревья. Для MVP
используется детерминированный набор правил по признакам — быстро и понятно пользователю.

В будущем `explainer.py` можно заменить на SHAP:
```python
import shap
explainer = shap.TreeExplainer(model)
shap_values = explainer.shap_values(features_df)
top_features = shap_values.argsort()[::-1][:3]
```

### 7.5. Fallback при недоступности ML

Это поведение **во время запроса recommendation**, а не глобального readiness: при падении ML после
успешного старта `/health/ready` может оставаться `up`, потому что зонд ML помечен как необязательный;
при `ML_GRPC_ENABLED=true` недоступный ML на **bootstrap** по-прежнему мешает запустить процесс
(`mlgrpc.NewClient` до поднятия HTTP).

Если gRPC вызов завершился ошибкой (таймаут, сервис недоступен, `ErrRankingNotImplemented`),
backend переключается на deterministic fallback в Go (`buildFallbackCandidates`):

```go
score = 3.0
     + (1 - budgetGap/budgetMax)     // ценовая близость
     + 2.0 × categoryMatch            // совпадение категории
     + 0.75 × interestMatches         // совпадения интересов
     + 0.25 × hasImage                // наличие изображения
     - 2.0 × alreadyInWishlist        // штраф за уже сохранённые
```

SLA: ответ ≤ 6 секунд при 200 кандидатах обеспечивается и ML, и fallback.

## 8. Технологический стек ML — обоснование выбора

### 8.1. Python 3.13

- Официально поддерживает `list[T]` / `dict[K, V]` аннотации без импорта `typing`
- Free-threaded GIL в 3.13 (experimental) даст прирост при multi-threaded inference
  в будущем
- ТЗ требует Python 3.13+

### 8.2. FastAPI для healthz

FastAPI выбран для HTTP `/healthz` эндпоинта по следующим причинам:
- Автогенерация OpenAPI схемы (пригодится для мониторинга)
- Async-first: работает в одном event loop с uvicorn, не блокирует gRPC thread
- Легковесный: `import fastapi` занимает ~50ms при холодном старте

### 8.3. gRPC для связи с backend

gRPC vs REST для ML inference:
- **Protobuf** сериализует данные компактнее JSON (бинарный формат): для 200 кандидатов
  экономия ~40% по размеру payload
- **Строгая типизация**: если протокол меняется, обе стороны не скомпилируются —
  ошибки обнаруживаются на этапе разработки, не в runtime
- **HTTP/2 multiplexing**: несколько запросов в одном соединении, меньше latency при
  параллельных рекомендациях
- **Health checking**: `grpc_health_v1` — стандарт, поддерживаемый Kubernetes и
  Docker healthcheck через `grpc_health_probe`

### 8.4. LightGBM 4.x

- inference на CPU < 5ms для 200 кандидатов × 9 признаков
- модель сериализуется в `pickle` (~1–5 MB), загружается однократно в singleton `Ranker`
- встроенная поддержка LambdaRank в API: `objective="lambdarank"`, `group=sizes_array`
- активная поддержка Microsoft: совместима с Python 3.14

### 8.5. Pandas + PyArrow для данных

Parquet как формат обучающего датасета:
- Колоночное хранение: для 9 числовых признаков PyArrow читает только нужные колонки
- Сжатие snappy по умолчанию: 25 000 строк × 15 колонок = ~750 KB против ~3 MB CSV
- Dtype-aware: `int8`, `float32` вместо generic `object` снижают потребление памяти

## 9. Plan: переход от синтетики к реальным данным

### 9.1. Этап 1 — накопление трекинга (0–30 дней после запуска)

Сервис начинает собирать события через `POST /api/v1/tracking/events`:
- `gift_view` — пользователь открыл карточку
- `wishlist_add` — добавил в список желаний
- `link_click` — перешёл на сайт магазина (самый сильный сигнал, implicit purchase intent)

### 9.2. Этап 2 — построение implicit feedback датасета

После накопления 10k+ событий запускается `jobs/refresh_popularity.py`:

```sql
SELECT gift_id,
       COUNT(*) FILTER (WHERE event_type='gift_view')     AS views,
       COUNT(*) FILTER (WHERE event_type='wishlist_add')  AS wishlist_adds,
       COUNT(*) FILTER (WHERE event_type='link_click')    AS clicks
FROM tracking_events
WHERE occurred_at > NOW() - INTERVAL '30 days'
GROUP BY gift_id
```

Метрика популярности: `popularity = views × 0.1 + wishlist_adds × 0.5 + clicks × 2.0`

Это **взвешенная комбинация** сигналов: клик ценнее добавления в wishlist, добавление
ценнее просмотра. Коэффициенты аналогичны практике YouTube/Netflix implicit feedback.

### 9.3. Этап 3 — переобучение с реальными метками

Для пар (запрос, товар), по которым есть трекинг, заменяем синтетические метки:

| Событие | Метка |
|---|---|
| `link_click` | 3 — максимальная релевантность |
| `wishlist_add` | 2 |
| `gift_view` > 10 сек | 1 |
| Нет событий | 0 (implicit negative) |

Запросы без трекинга продолжают использовать синтетику. Датасет становится **гибридным**,
постепенно смещаясь в сторону реальных данных по мере накопления.

### 9.4. Этап 4 — онлайн-A/B тест

Признак `model_version` в `RankResponse` позволяет backend-у логировать, какой версией
модели был сгенерирован результат. A/B тест: 50% трафика → `v0_1_0` (синтетика),
50% → `v1_0_0` (реальные данные). Победитель определяется по `link_click rate`.

## 10. Известные ограничения и пути улучшения

| Ограничение | Текущее состояние | Путь улучшения |
|---|---|---|
| Синтетические описания | "Декоративный свеча 4998. Отличный вариант…" | Реальные данные из WB/AliExpress |
| TF-IDF текстовое соответствие | Точность ~60% на синтетике | `sentence-transformers` + кэш эмбеддингов |
| Отсутствие popularity сигнала | Признак всегда 0 | После 30 дней трекинга — `refresh_popularity.py` |
| Одна валюта в модели | RUB/CNY смешаны как числа | Конвертация в RUB по курсу ЦБ РФ через `currency` поле |
| Нет personalization | Модель не учитывает историю пользователя | User embedding из wishlist + history |
| Холодный старт товара | Новый товар без трекинга | Content-only scoring через text embeddings |
| Нет gender в модели | Поле добавлено в схему, но не в `FEATURE_COLS` | Добавить `gender_male`/`gender_female` one-hot |
